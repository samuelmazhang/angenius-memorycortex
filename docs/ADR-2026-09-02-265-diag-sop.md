# ADR-265: cortex-diag.sh -- SOP for "why does this chunk have 0 relations?"

- Status: Accepted
- Date: 2026-09-02
- Author: Hermes (subagent dispatch) + 天行健 (decision)
- Related: ADR-262 (real-time relation graph), ADR-263 (P2 enhancements)

## 背景 (Context)

2026-09-02 补偿任务 (`deleg_5beaf825`) 期间, 我和子代理写了多个 ad-hoc
diagnostic SQL 查询来验证 "1881 停机期间漏算 relations" 的假设. docker
logs 抓到了 3 个 ERROR:

  1. `ERROR: column reference "created_at" is ambiguous at character 8`
     触发 query: `SELECT created_at::date, COUNT(*) FROM memory_chunks m
                  LEFT JOIN memory_relations r ON ... WHERE m.created_at > NOW() - ... `
     原因: SELECT 里有 `created_at::date`, WHERE/GROUP BY 里也有, 表别名 `m` 在 SELECT
     里被省略, 因为 LEFT JOIN 引入了第二个 `created_at` 列 (memory_relations 没有
     created_at, 但 table alias 是 m 仍 ambiguous with `m.created_at`).

     其实 PG 应该能 infer 只有一个 created_at 来自 `m`, 但当 m 创建_at 列 + WHERE
     里出现未限定列名 + GROUP BY 1 时, PG 报 ambiguous.

  2. `ERROR: cannot cast type jsonb to text[] at character 149`
     触发 query: `WITH own AS (SELECT tags FROM ...) SELECT ...
                  unnest(m.tags::text[]) ... ANY(ARRAY(SELECT jsonb_array_text ...))`
     原因: `m.tags::text[]` 直接 cast jsonb 到 text[] 不行. 需要先 `jsonb_array_elements_text`.

## 关键发现: **这些不是代码 bug**

docker logs 抓的 ERROR 来自 **ad-hoc diagnostic SQL** (子代理 + 我临时写的),
不是 cortex api_pg.py 里的 production SQL. 验证:

  * `tags ?| %s::text[]` 在 _sched_record_tag_shared_relations (api_pg.py:4224) 实测
    **正常工作** (psycopg2 自动把 Python list 转 text[]). 见 2026-09-02
    `verify-tag-shared-v2` chunk 成功创建 1 个 tag-shared relation.

  * api_pg.py 里所有 SELECT 都用 `r["..."]` 访问 dict 字段, 没有 ambiguous
    column 的 SELECT 语句.

**真问题**: ad-hoc diagnostic 查询容易写错, 但**目前没有 ops SOP**指导运维
或 agent 怎么安全诊断. 每次都得靠试错.

## 决策 (Decision)

加 `scripts/cortex-diag.sh` 脚本 (5.6 KB) -- 一键诊断任何 chunk 的
"为什么 0 relations" 问题. 6 步:

  1. chunk metadata (id, type, source, importance, archived, tags, embedding
     presence + dim, created_at)
  2. memory_relations involving this chunk (outgoing + incoming)
  3. memory_links involving this chunk (outgoing + incoming)
  4. tag overlap analysis: this chunk's tags vs all others, count overlap.
     Done correctly with `jsonb_array_elements_text` (the right way to
     unnest JSONB text arrays).
  5. embedding similarity: top-5 nearest neighbors by cosine distance,
     converted to cosine similarity (1 - distance).
  6. P2 worker state: both port 1880 and (if running) port 1881 worker_ids,
     processed counts, is_running, dead-letter count.

Then prints hints:

  * If 2 = 0 rows BUT 4 shows tag_overlap >= 2: hook missed a real match.
    Force-enqueue fixes it.
  * If 2 = 0 rows BUT 5 shows neighbors with cosine_sim >= 0.65: same fix.
  * If both 4 and 5 are below thresholds: 0 relations is correct, no action.
  * If 6 shows dead > 0: see /admin/maintenance/dead.

## Future work

  * Add `cortex-diag.sh` to README / runbook so on-call knows it exists.
  * When `pgvector` operators evolve, update the SQL templates in this
    script (tag-shared uses `?|` with text[] cast; similar uses
    `<=>` cosine distance).

## Verification

Run against `mem_20260902_000733_893141_fed2b1` (the chunk that recovered
1 relation in compensation):

  * Step 1: type=knowledge, tags={"verify-tag-shared","v6.5.1-test"},
    has_embedding=t, emb_dim=768.
  * Step 2: 1 tag-shared relation out (after compensation), 0 in.
  * Step 4: top overlap = 1 tag (verify-tag-shared is unique). Confirms
    why initially 0 relations (no 2-tag overlap existed at the time).
  * Step 5: top cosine_sim ~0.5 (below 0.65 threshold). Confirms no
    embedding-based relation should exist.

Output of step 6 + hints together make "why 0 relations" answerable in
seconds without writing SQL.
