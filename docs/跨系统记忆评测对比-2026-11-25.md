## 1. 一句话结论

Cortex 6.7.0 已完成**检索层 + 答案层双层全量实测**（1986 题、0 错误）：

- **检索层 recall@5 = 60.1%**，比 6.5.0 的 56.7% 提升 3.4pp，高于论文全部 RAG baseline（36.6–46.3%），略优于第三方 BM25 的 memory-pulse（57.4%）。
- **答案层（cats 1–4）token-F1 = 0.355、LLM-judge = 0.470、EM = 0.156**；cat5 正确拒绝率 78.6%。

**核心结论**：答案层补齐后，Cortex 的 judge（0.470）**低于主流记忆系统**（MemoryBear 统一 harness 下 Mem0 0.827、Zep 0.574），也低于 full-context baseline（0.729）。根因是检索层"找到正确 chunk"（60.1%）与答案层"chunk 里含精确答案"之间存在显著 gap——典型如 temporal 问题检索命中正确对话轮，但记忆原文只写 "recently" 而非 "7 May 2023"，reader 无法生成精确答案。**这是记忆内容粒度问题，不是检索排序问题**。

## 2. 口径说明（最重要，先读）

记忆系统评测有三层，数字不能跨层比较：

| 层级 | 指标 | 测什么 | 本轮 Cortex |
|---|---|---|---|
| L1 检索层 | recall@K / MRR / precision@K | 是否把正确的证据块找回来（objective，用 `dia_id` 匹配 ground truth） | ✅ 60.1% R@5 |
| L2 答案层 | EM / token-F1 | reader 基于检索证据生成短答案，与标准答案字面重合度 | ✅ F1 0.355 / EM 0.156（cats 1–4） |
| L3 判定层 | LLM-judge accuracy (J) | LLM 判定 reader 答案语义是否正确（主流宣传数字，0/0.5/1） | ✅ J 0.470（cats 1–4）/ 0.541（全量含 cat5） |

- 竞品 90%+ 几乎都在 **L3**，且多数只算 cats 1–4（1540 题，排除 adversarial），judge/reader 模型各异。
- Cortex 答案层管线：Cortex `/search` 取 top-5 → relay 网关 LLM（`free-auto` 别名，自动故障转移）作 reader 生成短答案 → 同一 LLM 作 judge 打 0/0.5/1。竞品的 judge 多为 gpt-4o 系，模型不同会系统性影响分数（见下）。
- Cortex 60.1% 在 **L1**，用全部 1986 题。
- **同一系统的 LoCoMo 分数在不同来源能差 20–40pp**（例：Zep 94.7% 自报 vs 75.1% 第三方 vs 57.39% MemoryBear 复跑），原因就是 judge 模型、reader 模型、是否 rerank、题集范围不同。
- 因此本报告把两类数字**分成两张表**，不做跨层排名。

### 4.3 检索层 → 答案层的 gap（关键发现）

2-hop 是最极端案例：检索层 R@5 高达 74.5%（全类最高），但答案层 judge 仅 0.223（全类最低）。根因不是"找不到证据"，而是**证据块内容粒度不足**：

- 例：Q "When did Caroline go to the LGBTQ support group?"，gold "7 May 2023"。
- 检索命中正确 chunk（`dia_id` 匹配，R@5 算命中），但 chunk 原文只有 "Caroline attended an LGBTQ support group **recently**..."，无具体日期。
- reader 只能答 "Recently." → judge 0.0。

即：**检索层用 `dia_id` 判命中是"宽松命中"（找对轮次即可），答案层要求"chunk 内含精确答案"**。二者 gap 反映 Cortex 的记忆写入策略保留了语义但未保留精确属性（日期、数量、专名）。这是产品短板，指出改进方向：写入时做属性抽取/结构化，而非仅存原始对话句。

### 4.4 与竞品答案层的同口径定位

见下一节表 B。需注意：Cortex 的 reader/judge 均为 `hy4-flash-free`，竞品统一 harness（MemoryBear）用 gpt-4o 系 judge；judge 模型不同会带来系统性偏差，故 Cortex judge 0.470 应视为**量级参考**，非严格 apples-to-apples。要严格对齐需实现 Cortex backend 接入 Mem0 开源评测框架，用相同 reader/judge prompt 与模型。

## 6. 结论与建议

**能说的**：
1. Cortex 6.7.0 检索层 R@5 60.1%，在同口径的 LOCOMO 检索对比中处于第一梯队（高于论文 baseline，略优于第三方 BM25）。
2. 6.6/6.7 的重构（PPR、rerank 双门控、配置统一）带来了可测增益：R@5 +3.4pp，2-hop +7.2pp，且 1986 题 0 错误、生产稳定。
3. 答案层已补齐：cats 1–4 的 F1 0.355 / judge 0.470，cat5 正确拒绝率 78.6%，1986 题 0 错误。

**不能说的 / 短板**：
1. **答案层处于主流系统下游**：judge 47.0% 低于 MemoryBear harness 全部竞品（53.7–91.5%），F1 0.355 中下。核心瓶颈是 memory chunk 的**内容粒度**而非检索排序——2-hop 检索 R@5 74.5% 但答案层 judge 仅 0.223，证据块缺少精确日期/数量/专名。
2. **严格排名仍不可得**：Cortex judge/reader 用 hy4-flash-free（非 gpt-4o 系），prompt 也未与竞品框架对齐，0.470 只能作量级参考。
3. temporal 检索层 38.5% + 答案层 judge 0.229 双弱，是结构性短板。
4. 延迟 p50 从 136ms 升到 178ms（rerank 代价），需在吞吐与精度间权衡。

**下一步（按优先级）**：
1. **提升记忆写入粒度（最高 ROI）**：在 `/chunks` 写入时做属性抽取（日期、数量、专名、关系），存结构化字段；让 reader 能直接引用精确属性，而非仅靠原始对话句。预期对 2-hop/temporal 答案层提升最大。
2. **严格同口径复跑**：实现 Cortex backend 接入 Mem0 开源评测框架（`github.com/mem0ai/memory-benchmarks`），用相同 reader/judge prompt 与 gpt-4o 系 judge，得到真正 apples-to-apples 分数。
3. temporal 专项：日期感知 reranker（ADR-078 已列为 follow-up）。
4. 双层快照（`_locomo_full_sample_6_7.json`、`_locomo_answer_full_6_7.json`）纳入一致性检查与 CI。

1. 用户关于"低分源于数据/模型不同"的质疑**部分成立**：在模型、题集、代码全部锁死的前提下，仅替换数据质量，judge 就提升 5.5pp、F1 提升 5.6pp、全量 judge 提升 5.8pp——证明此前的低分里有相当一部分是**数据表示为因**，而非单纯模型能力或检索排序。
2. 数据层修复的最高 ROI 方向得到验证：**精确属性（时间/实体）的可检索性**比排序优化更能拉升答案层。
3. 但仍未达到主流上游系统（Mem0 82.7%、MemOS 84.3%、MemoryBear 91.5%），差距主要来自 judge 模型口径与 harness 对齐、以及 1-hop/temporal 的副作用。
4. 下一步：① 时间锚点结构化存字段（消除 1-hop/temporal 退化）；② Cortex backend 接入 Mem0 benchmark 严格同口径复跑；③ 用 gpt-4o 系 judge 复核以消除模型偏差。

## 9. cat1（1-hop）短板专项：去重 + 聚合题扩召回 A/B（2026-11-26）【负面结论，未落地】

### 9.1 诊断（数据驱动）
cat1（282 题）在 v2/v3 退化，逐题翻转显示 **98% 的退化是 reader 输出 `Unanswerable`**，而非答错：OLD 对→v3 错 68 题、反向仅 18 题，其中 67 题 v3 直接拒答。拒绝率 OLD 20.6% → v3 38.6%。

根因：cat1 大量是**多值聚合题**（列举/计数，gold 有 3–7 个值，分散在多轮）。检索 top-5 被两类噪音占据——① 带 `[时间] Speaker:` 前缀的近重复变体（同一 `dia_id` 的 turn + observation 各存一份）；② 无 `dia_id` 的 session summary（与问题语义相近但无具体事实）。关键事实进不了 top-5，小模型保守拒答。

### 9.2 A/B 设计（消费侧，不改服务 / 不重新 embed）
脚本 `server/tests/integration/_locomo_dedup_ab.py`，三 mode 共享同一 /search 语料、同一 reader/judge 模型、同一 prompt，唯一变量是喂给 reader 的上下文列表：
- `baseline`：现状 top-5 `grounded_context`
- `dedup`：从 pool=12 按 `metadata.dia_id` 折叠近重复（优先 observation 变体）+ 过滤无 dia_id 的 session summary，取 top-5
- `dedup_expand`：聚合题（正则覆盖 cat1 的 20.2%，57/282）扩召回 pool=14→cap=8 + 去日期噪音

### 9.3 全量结果（cat1 282 题，同模型同数据）

| mode | judge | token-F1 | 拒绝率 | avg ctx |
|---|---:|---:|---:|---:|
| baseline | 0.3262 | 0.2302 | 39.0% | 4.91 |
| dedup | 0.3327 | 0.2334 | 36.9% | 2.78 |
| dedup_expand | 0.3121 | 0.2257 | 41.5% | 2.80 |

配对 bootstrap（5000 次）：Δdedup=+0.0089，95%CI [−0.0142, +0.0338]；Δexpand=−0.0142，95%CI [−0.0355, +0.0071]。**两种改动相对 baseline 均不显著（CI 含 0）。**

### 9.4 结论：不落地，保留为负面证据
1. **按 `dia_id` 去重无显著收益**。丢分案例显示：LOCOMO 的 turn 与 observation 虽同 `dia_id`，但**并非简单重复，常是同一对话的不同侧面**。强行折叠到 2 条会丢补充证据（`Becoming Nicole` 的 chunk 被折掉 → 从答对变 `Unanswerable`）。baseline 的 5 条上下文是信息密度的经验甜点。
2. **聚合题扩召回反而略降**（不显著但有净丢分趋势：base 对→新错 9、base 错→新对 5）。扩召回把无 `dia_id` 的无关 session summary 拉进上下文，稀释有效信息。
3. **cat1 的瓶颈不在"上下文条数/重复度"，而在更深层**：多值事实分散 + 小模型（hy4-flash-free）面对不确定材料时倾向保守拒答。这是 reader 模型能力 / prompt 策略问题，不是检索去重能解决的。
4. 下一步若继续攻 cat1，方向应是：① 更强 reader 模型（消除小模型保守偏差，但受免费 relay 批量 429 限制）；② 针对多值题的 reader prompt（明确要求"列出所有提到的事实"而非"确定就答、不确定就拒答"）；③ 重注入一版纯文本（去 v2 时间前缀）对照，隔离前缀污染。均不属于"去重/扩召回"，需另行评估。
