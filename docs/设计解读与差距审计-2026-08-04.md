## 一、热度（Heat）机制：设计意图

设计文档中"热度"一词没有显式命名，但**散布在三处语义合并**就是热度：

### 1.1 衰减率 + 召回加权（设计 §1.2 表）

| 层级 | 衰减率/天 | 召回加权 | TTL |
|---|---|---|---|
| short_term | 0.5 | × 1.2 | 7 天 |
| medium_term | 0.3 | × 1.1 | 30 天 |
| long_term | 0.1 | × 1.05 | 永久 |

**解读**：这就是 **Ebbinghaus 衰减曲线** 的离散化版本。每层有自己的衰减率。**含义**：一条 chunk 即使在 TTL 内不被访问，它的"信号强度"也会随天数自然衰减；一旦被访问，则在搜索路径上获得加权。

### 1.2 access_count 触发重要性升级（设计 §1.2 + §2.1）

```python
# 重要性动态升级：高频召回自动升级到 long_term
if access_count >= 10 and importance < 10:
    importance += 1
```

**解读**：这是"热度 → 持久化"的**关键桥**。一条 chunk 不一定初始就很重要（importance 低），但只要高频被访问 10 次以上，就自动 +1 重要度，最终进入 long_term 永不被 TTL 淘汰。

### 1.3 access_stats 表（设计 §2.2）

```sql
CREATE TABLE memory_access_stats (
    memory_id TEXT PRIMARY KEY,
    access_count INTEGER DEFAULT 0,
    last_access_at TEXT,
    relevance_score REAL DEFAULT 0.0  -- 由评估回路写入
);
```

**解读**：热度数据的**物理载体**。三个字段分工：
- `access_count`：纯召回次数（每次 search 命中 +1）
- `last_access_at`：最近召回时间（用于 TTL/衰减计算）
- `relevance_score`：评估回路给的"实际有用度"分数（与 access_count 不同）

### 1.4 检索路径上的热度应用（设计 §5.1 composite score）

```python
composite = 0.6 * rrf_norm
          + 0.4 * sim_effective
          + 0.05 * (importance / 10)
          + 0.1  * (1 / (1 + 0.05*age))
          + 0.1  * relevance          # ← 这里用到 access_stats 推导
```

**解读**：热度的**搜索侧反馈**。`relevance` 由 access_stats 推导（0~1），`+0.1*relevance` 把"被评估回路判定为有价值的记忆"在最终排序里加权。

## 二、推翻（Reinforce / Override）机制：设计意图

"推翻"一词设计文档没有显式命名，但有 4 处等价语义：

### 2.1 关联强度衰减（设计 §2.1）

```python
RELATION_STRENGTH_DECAY = 0.95  # 关联强度衰减因子
```

**解读**：每过一段时间没共同召回，两条记忆的"关联强度"按 0.95 因子衰减。这等价于**"旧关联自动被推翻"**——长期不用的关联会被弱化直至被新关联取代。

### 2.2 重复合并 + 保留重要性高的（设计 §2.1 + §2.3）

```python
# 相似度 > 0.9 的记忆自动合并
similarity > 0.9 → 合并：保留 importance 高的，删除低的
```

**解读**：**显式的"以新换旧 / 以高换低"的推翻逻辑**。新来的高 importance 记忆会吞掉旧的低 importance 近似副本。

### 2.3 矛盾检测（设计 §4.1）

| 功能 | 触发 | 写入方式 |
|---|---|---|
| 矛盾检测 | Cron / API | metadata 标记，不删除 |

**解读**：矛盾检测是"推翻"的**安全模式**——发现矛盾时**不直接覆盖**，而是打 metadata 标记，由人或后续 LLM 决定。这避免了错误推翻。

### 2.4 重要性动态升级（设计 §1.2）

`access_count ≥ 10 → importance += 1` 也是一种**柔性推翻**——旧认知被新证据（高频召回）逐步推翻。
