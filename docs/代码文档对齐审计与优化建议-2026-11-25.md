## 1. 执行摘要

Memory Cortex 是一个**实现成熟度明显高于文档成熟度**的项目：核心引擎（PG+pgvector、多路召回+CE 精排、冲突解决、RAPTOR、PPR 图谱、多 worker 维护队列、OTel）已迭代到 v6.6.0，但对外文档大面积停留在 v5.3.x，版本标识在 5 处互相矛盾。本次已对齐 3 份主文档（README / 文档索引 / 架构总览）。

最高优先级的技术债：① 单一 6538 行 `api_pg.py` 承载 118 路由且 `/endpoints` 目录陈旧；② 配置双源（`CortexConfig` 被主入口绕过）；③ 已知重复代码块与遗留分支；④ feature flag 默认关导致"实现了但没生效"的能力（RAPTOR/rerank/graph 等）；⑤ 文档与版本漂移。

## 4. 优化意见（按优先级）

### P0 — 影响正确性 / 可维护性

1. **拆分 `api_pg.py` 并让端点目录自动生成**
   - 现状：单文件 6538 行 / 118 路由；`ENDPOINTS_CATALOG`（L572-662）仅 89 条且含幽灵路由（`/mode/set`、`/rumination/debug-abstract` 无对应装饰器）。
   - 建议：按域拆分为 `routers/{chunks,search,graph,relations,forgetting,conflict,admin}.py`，用 FastAPI `APIRouter`；`/endpoints` 从 `app.routes` 运行时生成，杜绝手工目录漂移。
   - 收益：消除"文档/目录与代码不一致"的根源，降低合并冲突与新人上手成本。

2. **统一配置源**
   - 现状：`CortexConfig`（config.py L11-120）声称单一配置源且强校验 `EMBEDDING_MODEL_PATH`，但 `api_pg.py` L43-49 直接 `os.getenv` 绕过它；根 `.env.example`（POSTGRES_*/OTEL_*）与实际 `.env`（PG_*/CORTEX_PORT）字段不重合。
   - 建议：主入口改为从 `CortexConfig` 读取；提供 `config.py` 的兼容 getter；统一 `.env.example` 为真实字段的超集并注明必填/可选。
   - 收益：消除"配置写了却不生效"类隐蔽 bug（历史上已发生过 embedding 静默降级污染向量空间）。

3. **删除已知重复/遗留代码**
   - `api_pg.py` L2837-2858 与 L2859-2880 为 RAPTOR 候选追加逻辑的逐字重复（已确认）。第二次循环因 `_in_pool` 重建而不会新增，但属明确维护隐患。
   - `scheduler.py` Phase 1 in-memory deque + legacy daemon thread（L46-48/190-207/572-665）与生产队列并存。
   - 垃圾文件：`api_pg.py.bak.1786877256165`、根/`server/`/`server/src/` 三处 `NUL`、`ssh_host_key_*.pub`。
   - 建议：删重复块；给 legacy 分支加 `if False` 注释或直接移除；把备份移入 `backups/` 并加入 `.gitignore`。

### P1 — 能力"实现了但没生效"

4. **feature flag 默认关导致能力沉默**
   - 实测默认：`MEMORY_FEATURE_RAPTOR=0`、`MEMORY_FEATURE_RERANK=false`、`MEMORY_FEATURE_GRAPH_PPR` 默认开但需请求 `include_related`。
   - 建议：在 `/health` 或新增 `/capabilities` 中暴露各 flag 的**实际生效状态**（当前 `/health` 只有 chunks/relations/vectors）；文档明确"开启方式 + 前置模型/依赖"。
   - 收益：运维和接入方（含 WorkBuddy）能判断是否真的启用了精排/RAPTOR，避免"以为用了其实走粗排"。

5. **兼容端点补齐参数或明确弃用**
   - `/search/hybrid`、`/search/tts` 只接受 q/limit；`/reindex`、`/chroma/cleanup` 在 PG 后端为 no-op。
   - 建议：要么让兼容端点透传 `MemorySearchRequest` 全参数，要么返回 `410 Gone` + 指向 `/search`，并在 `ENDPOINTS_CATALOG` 标记 deprecated。

6. **把 cron 维护与 P2 队列合并为单一调度视图**
   - 现状：写入维护走 `ConsolidationScheduler` 队列；遗忘/巩固走外部 cron（`ops/maint/`）；两套脚本（旧 `server/scripts/maintenance_daily.sql` 与新 `ops/maint/`）并存。
   - 建议：统一为"一个调度器 + 多任务类型"，通过 `/admin/maintenance/*` 暴露状态；用 `docs/RUNBOOK.md` 单一入口描述。

### P2 — 工程质量 / 长期演进

7. **OTel 指标导出补完**
   - `/metrics` 手写 20 项 cortex_* gauge/counter 可用，但 OTel 指标路径为 `pass` 占位（L6513-6524）。
   - 建议：接入 ` observability.metrics.memory_reader` 输出真正 histogram；或移除占位注释避免误导。

8. **spreading activation 回迁前先做真实语料 A/B**
   - 现状：v7 仅在 `experiments/v7-spreading-activation/` POC（ADR-073/074）。
   - 建议：用 LoCoMo 1986 题在"PPR vs PPR+spreading"上做对照，达到显著增益再回迁生产路径。

9. **安全：CORS 全放行 + 无认证**
   - `api_pg.py` L493 `allow_origins=["*"]`，所有 REST/MCP 端点无认证。
   - 建议：至少在生产加可选 API-key/bearer（`CORTEX_API_TOKEN`），CORS 收敛到已知 agent origin；MCP `/mcp/` 同样受保护。
   - 注意：内网 127.0.0.1 部署可暂缓，但接入 WorkBuddy 等更多客户端后风险上升。

10. **测试与契约回归**
    - 已有 `openapi_baseline.json`、wiring 源码检查测试（好做法）。
    - 建议：加一项 CI 检查——`VERSION` 与 `/health` 版本一致性、`ENDPOINTS_CATALOG` 与 `app.routes` 一致性、README 标题版本与 VERSION 一致性，防止本次修复的漂移再次发生。

## 5. 加强方向（战略层）

1. **多租户/隔离强化**：当前 WorkBuddy 与 Arcadia 默认共享全局记忆（不传 user_id）。建议为 connector 增加 `user_id` 命名空间配置（WorkBuddy 侧可选隔离），并在写入时强制 origin 绑定以区分来源可信度。
2. **记忆质量闭环**：把 `memory_access_audit` 的查询/命中数据接入 relevance 反馈回路（ADR 评估回路已有设计），让 `_three_factor` 的权重可基于线上数据自动校准，而非固定经验值。
3. **可观测性产品化**：`/capabilities` + `/metrics` + 结构化日志（含 chunk_id/query/user_id）三件套，配合 `cortex-diag.sh` 形成"发现→定位→验证"闭环。
4. **接入层生态**：沿用本次新增的 `connector/workbuddy/` 模式（SKILL.md 行为契约 + MCP 数据通道 + smoke 自检），为更多 agent runtime 提供低代码接入模板。
5. **版本与文档工程化**：把"版本权威来源 + 文档同步清单"写入 CONTRIBUTING，配合 CI 断言，避免 5 处版本漂移重演。
